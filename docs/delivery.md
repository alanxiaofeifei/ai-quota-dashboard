# GitHub 与个人 ChatGPT Sites 交付

## 当前状态与发布条件

开源主仓为 [alanxiaofeifei/ai-quota-dashboard](https://github.com/alanxiaofeifei/ai-quota-dashboard)，已由用户创建并核实公开可访问。GitHub 是功能源码的唯一主仓；本地变更的提交与推送状态以实际 Git 结果为准。

用户另授权一个私有核心备份仓库。同步方向为 **公开主仓 → 私有核心备份 → Sites 部署镜像**；私有仓库的名称、URL 和部署身份不写入公开文档。私有备份保留自己的初始历史和私人 README，并核对功能源码指纹；不能把私人配置、账户数据或部署凭据反向合并到公开主仓。

个人在线版默认使用 **ChatGPT Sites 的 owner-private 托管**，只允许所有者访问。用户已授权后续个人站点，但选择等待至少一个自动采集源通过阶段 0 后再部署看板。**本额度看板尚未创建或部署 Site；其他既有 Site 不在本次修改范围。** 后续按该条件继续交付，不另设重复的发布批准步骤。

阶段 0 的判断仍以[验收清单](phase-0.md)为准。GitHub 仓库、离线解析器或测试通过，不能替代真实自动采集验证，也不能提前把演示数据作为在线个人额度。

## 一份功能源码与可核对的版本

当前主仓交付阶段 0 工具和 Windows 本地只读原型；网页、同源本地 API、SQLite 与构建脚本都保留在 GitHub。尚无后台自动采集或 Sites 部署。后续功能仍先进入公开主仓，再从同一版本生成私有核心备份与部署内容，避免分别维护。

核心备份保留已有源码、测试、依赖锁文件和工具链；未来还须包含可移植的构建、数据迁移及配置模板。供应商特定的项目身份、绑定和运行配置独立保存，迁移托管商时不重写产品核心。私有仓库也不存放 AI 平台凭据或真实额度报告。

每次发布登记以下来源信息：

- GitHub 仓库 URL 与已验证的完整提交 SHA。
- 参与部署的功能源码清单：排序后的相对路径及每个文件原始字节的 SHA-256；再对清单计算 SHA-256。
- 工具链、锁文件与成功检查结果；使用该源码构建的归档及其哈希。
- Sites 私有源码提交、保存版本和部署结果，保留它们与 GitHub 来源提交的对应关系。

功能源码清单必须涵盖网页、服务端、共享契约、构建脚本及依赖锁文件。排除项仅限独立部署身份、生成产物和运行状态，并明确列出；不得把业务代码或权限逻辑排除在一致性核对之外。

未来 Sites 的 `.openai/hosting.json` 包含个人 Site ID、托管目录及资源绑定。该部署身份与公开仓库的通用源码分开保存；公开仓库届时应提供可复现的通用模板，不能填入个人部署身份。凭据、运行时变量、个人额度及缓存不进入公开仓库或发布归档。

因此，Sites 的私有部署提交可能因个人托管元数据而不同于 GitHub 提交。发布记录同时保留两个完整 SHA，**功能源码的字节及清单哈希必须一致**，不能宣称不同 Git 树拥有相同提交 SHA。

## 本地源码一致性工具

仓库提供无需第三方依赖的 Node.js 工具。先提交功能源码，再将报告保存到 `reports/` 等生成目录：

```sh
node scripts/source-manifest.mjs
node scripts/source-manifest.mjs --verify reports/source-manifest.json
node --test scripts/source-manifest.test.mjs
```

第一条命令向 stdout 输出 JSON，可由调用方保存为 `reports/source-manifest.json`。工具不会创建该目录，不执行网络操作，不读取 Git 凭据，不修改 Git 仓库。仓库未初始化、没有 HEAD，或功能源码存在暂存／未暂存／未跟踪变更时拒绝生成。明确功能目录中即使被 `.gitignore` 忽略的新源码也会阻止发布。

默认清单包含 Rust 源码、测试与合成夹具、Cargo 清单／锁文件／工具链、`scripts/`、`.github/`、`browser-extension/`、`web/`，以及后续可能新增的 `site/`、`shared/`、`app/`、`worker/`、`db/`、`drizzle/`、`public/`、`crates/` 和根目录包清单、锁文件、构建配置。新增功能目录或特殊构建输入时，先更新工具范围与测试。

排除文档、README、独立 `.openai/` 托管身份、环境变量文件、依赖缓存及生成目录。`scripts/build/` 和 `src/build/` 等源码路径仍被覆盖；构建产物、报告和运行状态不参与功能一致性。工具拒绝符号链接和可穿越路径，文件名中的换行通过 Git NUL 分隔及 JSON 转义处理。

清单按 UTF-8 路径字节排序，逐文件计算原始字节 SHA-256，再对标准 JSON 文件列表计算 `functional_source_sha256`。验证时核对清单结构、完整文件集合及哈希，允许个人托管元数据造成的 Git SHA 差异。它验证内容一致性，不能代替发布签名、测试或真实采集验收。

私有核心备份可在根目录保存 `core-backup.json` 作为来源清单；它只记录来源提交和源码哈希，不包含账户数据。该清单本身属于来源元数据，不参与自身的功能指纹。若存在该文件，CI 使用同一个工具核对：

```sh
node scripts/source-manifest.mjs --verify core-backup.json
```

公开主仓没有该备份清单时跳过此检查；私有镜像不能另改功能代码或工作流来绕过一致性核对。

## 门槛通过后的交付顺序

1. 固定并检查 GitHub 来源提交，确认功能、测试和许可记录完整。
2. 更新私有核心备份，保留其独立历史和私人 README；生成并核对 `core-backup.json`。
3. 从该版本准备 Sites 镜像，写入独立托管身份，再核对功能源码清单。
4. 将精确部署源码推送到 Sites 返回的远端与分支，从同一源码构建并打包，保存和部署同一版本。
5. 确认原生 Sites 返回成功与实际 URL；登记 GitHub SHA、备份 SHA、功能清单哈希、Sites SHA 和部署版本，作为升级与回滚依据。

后续在 Sites 发起的功能修改也要先回到 GitHub，完成验证后再生成镜像。回滚选择已经登记的来源版本并恢复匹配的数据迁移状态，不只替换网页文件。

上述是版本一致性的交付流程，**不是常驻自动同步服务**。当前没有为持续同步创建 PAT、后台守护进程或定时任务；具体推送与核对以实际 Git 和 CI 结果为准。不能仅因存在多个远端就宣称后台自动同步已完成。

## 托管与隐私边界

个人托管的默认目标是 ChatGPT Sites；Cloudflare 直部署或普通自托管仍保留为未来可选路径。它们共用摘要契约，不改变本地优先原则。

AI 平台密码、Cookie、访问／刷新令牌、完整浏览器会话和聊天始终留在本机。未来即使在线功能接收摘要，也只接收经过白名单投影的额度字段，并实施所有者身份验证、设备授权与撤销、保留和删除机制。私人 Site 的访问控制不替代应用内的数据归属检查。

GitHub 开源发布不能包含真实账户夹具、个人摘要、站点凭据、运行时日志或构建缓存。来源清单用于核对代码，不能作为上传个人数据的理由。
